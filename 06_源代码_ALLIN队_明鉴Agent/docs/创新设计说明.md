# 授权差异检视

队伍：ALL IN队
学校：中央财经大学
成员：石轩赫

## 创作理念

用户希望自然语言银行不只减少点击，还能让自己看清并控制资金操作。用户依次选择“可解释安全银行”“对话加透明任务单”和“授权差异检视”。作品将这一方向落实为可检查的变更与授权协议，重点回答：用户改动了什么，风险与资金影响如何变化，旧的同意为什么不能继续使用。

## 机制

1. 参数预览。修改窗口立即展示新旧收款人、金额、风险与预计余额，帮助用户比较。该预览不能授权扣款。
2. 服务端变更证据。保存时以同一账本状态计算修改前后任务单，记录直接修改和受影响的后续转账。版本递增并清空旧审阅凭证及验证码。
3. 审阅快照。打开确认窗口时，服务端签发随机审阅令牌，哈希绑定计划、节点、版本、参数、余额、日累计和日期，且只保留令牌哈希。界面使用服务端资金影响展示。
4. 执行前验证。服务端校验令牌、有效期和当前资金状态，检查所需权限及模拟强验证。变化后要求重新审阅，不能以旧确认执行新影响。
5. 可追溯回执。成功交易关联计划版本、授权快照哈希和唯一工具回执，变更记录纳入审计哈希链。

## 主演示

初始余额25000元、日累计0元。先说“查询余额，然后给张三转200元”，余额查询自动完成，200元转账待确认。将收款人改为李四，金额改为1200元。系统展示余额影响从24800元变为23800元，风险从黄色升级红色，计划从v1变为v2。旧确认失效，新版本必须重新审阅并完成模拟验证。执行后回执显示1200元已从本地模拟账本扣减。

## 可验证价值

测试直接攻击旧版本、旧令牌、过期令牌以及另一个计划改变余额后的旧快照。修改前一步后，后续转账的日累计风险也会重新计算。界面展示、服务端约束和测试证据相互对应。

本作品的差异化在于把变更可视化、资金状态绑定和授权失效组合成可运行的银行任务流程。不主张哈希、版本控制、DAG或交易确认本身为原创，也不保证全球首创。当前已接入本地Qwen3大模型和手机TOTP，但没有接入真实银行；所有资金均为合成沙箱数据。
